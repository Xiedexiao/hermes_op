# Hermes Operator 产品设计文档

## 1. 文档目标

本文档用于定义一个全新的 `Hermes Operator` 产品方向。目标不是把 `repos/` 下的多个项目简单拼接，也不是接入这些项目的现有代码，而是以 `hermes-agent` 的功能与行为作为复刻基线，以 `TuriX-CUA` 的桌面软件操作能力作为重点 benchmark，再从其他项目中抽取增强思路，形成一个完全绿地开发的桌面级 Agent 产品。

默认前提如下：

- 首个版本优先服务高频知识工作者与轻量团队，而不是超大企业的统一 AI 门户。
- 首个版本优先做 macOS / Windows 桌面端，不以浏览器端作为主战场。
- 首个版本强调“决策 + 执行 + 记忆”的闭环，不追求一次性覆盖所有业务场景。

## 3. 产品机会判断

当前桌面 AI 工具大致分成三类：

1. 聊天型 AI：会回答，但不会真正完成工作。
2. 自动化型 Agent：会执行，但缺乏可靠的前置判断与过程可视化。
3. 企业知识型平台：会检索，但离用户真实桌面工作流很远。

这三类产品之间存在明显断层：

- 在“做之前”，缺少真正面向任务结果的情境预演。
- 在“做的过程中”，缺少可解释的多 Agent 治理和人工介入机制。
- 在“做完之后”，缺少高保真记忆与自动成长能力。

因此，新产品不应定义成“另一个桌面聊天窗口”，而应定义成：

**一个以 Rust 重写的 Hermes 等价 Agent Core 为能力基线、以桌面软件操作为主战场、并以超越 TuriX 为目标的桌面执行系统。**

它的核心闭环是：

**理解目标 -> 观察桌面上下文 -> 生成计划 -> 操作桌面软件 -> 校验结果 -> 沉淀记忆**

## 4. 产品定义

### 4.1 产品名称

`Hermes Operator`

可选副标题：

- Decision-to-Action Desktop OS
- 会研究、会预演、会执行、会记忆的桌面 Agent

### 4.2 一句话定位

`Hermes Operator` 是一个面向知识工作者与轻团队的 desktop-native operator。它以 Rust 从零实现一个与 `hermes-agent` 功能和行为等价的 Agent Core，把操作桌面软件、跨应用完成任务、回收执行结果作为产品主线，并把超越 `TuriX-CUA` 的桌面软件操作能力作为重点目标；知识、记忆、治理、推演和成长能力则服务于这条主线，而不是反客为主。

### 4.3 核心价值主张

- 不只是回答问题，而是亲自操作软件并交付任务结果。
- 不只是一个桌面壳，而是对 `hermes-agent` 能力体系的 Rust 绿地重写与桌面执行产品化。
- 不只是自动执行，而是在复杂任务上可叠加记忆、研究、审议和推演能力。
- 不只是完成一次任务，而是在每次任务后变得更懂用户和更懂桌面工作流。

## 5. 目标用户

### 5.1 核心用户

1. 创始人 / 产品负责人 / 业务负责人
   - 需要快速理解复杂问题、比较方案、生成结论、推动落地。
   - 经常在浏览器、文档、即时通信、表格、演示文稿之间切换。

2. 研究分析人员
   - 包括投研、咨询、行业研究、战略分析、政策研究等角色。
   - 需要大量检索、比对、归纳、形成报告，并做情景推演。

3. 运营与行政负责人
   - 需要跨 SaaS、文档、邮件、即时通信和本地文件完成完整流程。
   - 对“能直接执行”比“能聊天”更敏感。

### 5.2 次级用户

1. 高阶开发者与自动化工程师
   - 需要把 CLI、脚本、浏览器和桌面 GUI 工作流统一起来。

2. 小团队的 AI 负责人
   - 希望让团队共享知识、沉淀流程、形成标准化代理执行方式。

### 5.3 首版非目标用户

- 仅希望做闲聊问答的普通消费者用户
- 需要复杂组织权限、合规审计、SSO 的大型企业采购场景
- 需要强行业垂直模板但不关心桌面执行能力的纯 SaaS 客户

## 6. 核心使用场景

### 场景 A：高价值任务处理

用户给出一个复杂目标，例如：

- “基于本地客户资料和最近行业动态，帮我准备明天的客户拜访方案，并生成演示稿。”
- “分析这次舆情的风险演化路径，给出三种应对预案，再把推荐方案拆成执行步骤。”

系统完成：

- 检索本地和在线信息
- 汇总上下文
- 做多方案预演
- 组织多 Agent 审议
- 自动生成文档、PPT、行动清单
- 必要时直接操作桌面应用执行后续步骤

### 场景 B：跨应用办公自动化

例如：

- 从邮件或 IM 中拿到任务
- 读取附件与表格
- 生成报告或图表
- 打开文档应用插入内容
- 最终通过邮件或 IM 回传结果

这个场景是产品的主战场，核心由 Rust 重写的 Hermes 等价 Agent Core 驱动，并以 `TuriX-CUA` 作为桌面软件操作 benchmark，目标在成功率、稳定性、覆盖面和恢复能力上超越它。

### 场景 C：持续项目工作台

例如用户围绕一个长期项目持续工作：

- 新资料加入知识集
- 历史讨论、结论、失败原因被自动归档
- 下次启动时，Agent 能直接恢复“项目上下文”
- 完成任务后，自动萃取流程模板与技能建议

这个场景是在核心执行能力稳定后叠加的增强层，主要继承 `mempalace` 与 `DeepTutor` 的“成长型工作流”。

### 场景 D：决策预演与风险控制

例如：

- 推演舆情扩散路径
- 推演对外公告策略影响
- 推演某个商务动作对不同角色的反馈
- 比较多个执行策略的风险/收益/资源要求，并把结论保存为 scenario run

这个场景属于高阶增强能力，不是首版主线，但当前版本已经先落地 Mission 级的文本化 baseline / option 对比、结构化 option card 存储、变量权重注入、recommendation rationale、mission-level comparison matrix 和 path evolution；保存 scenario run 后也会自动进入 Council / Execution review handoff。

## 7. 差异化定位

### 7.1 相比纯聊天类产品

`Hermes Operator` 的差异在于：

- 它默认以“操作桌面软件并完成任务”为目标，而不是先做聊天。
- 它有任务状态、执行计划和结果产物，不是单轮问答。
- 它能跨本地桌面与外部工具执行，而不是停留在文本层。

### 7.2 相比纯 RPA 或 CUA 产品

它不是“看见什么点什么”的自动化工具，而是：

- 先由 Rust 重写的 Hermes 等价 Agent Core 理解任务
- 再做 Mission 级 baseline / option cards 比较
- 再保存 recommendation 和 rationale，并按 handoff policy 进入 Council / Execution review
- 再做执行审批
- 再进入桌面软件操作

因此它更像“会思考、会操作软件、会自校验的桌面执行官”，而不是“会点鼠标的机器人”。

### 7.3 相比企业知识库 / AI 门户

它的核心不是“统一检索入口”，而是“从知识到动作的闭环”。

`Onyx` 给了检索和研究能力，但 `Hermes Operator` 更进一步，把：

- 知识理解
- 任务编排
- 执行动作
- 记忆沉淀

放进同一个桌面工作流里。

## 8. 产品理念

### 8.1 决策先于执行

任何高成本动作都应该先经过理解、预演与审议，而不是直接执行。

### 8.2 本地优先与用户可控

敏感文件、长期记忆、执行日志应优先存放本地，用户能看见、暂停、复盘、删除。

### 8.3 多 Agent 不是越多越好，而是越清楚越好

多 Agent 的价值来自角色清晰、责任清晰、状态可见，而不是后台并发得越多越高级。

### 8.4 每一次任务都应该留下成长性资产

不是只留下最终结果，而是留下：

- 可检索上下文
- 可回放过程
- 可复用的技能和模板
- 对用户偏好的更深理解

## 9. 产品核心设计

### 9.1 一条主线：Mission 驱动

产品围绕 `Mission` 工作单元展开。一个 Mission 不是一句 Prompt，而是一个完整工作对象，包含：

- 目标
- 约束
- 相关资料
- 推演结果
- 审议记录
- 执行计划
- 产物
- 复盘结论

### 9.2 两个闭环

#### 工作闭环

Research -> Simulate -> Review -> Execute -> Deliver

#### 成长闭环

Archive -> Recall -> Learn -> Skillize -> Personalize

前者保证任务能做完，后者保证系统越用越强。

### 9.3 七层能力架构

1. `Hermes Core`
   - 任务理解、工具编排、技能执行、长时间运行

2. `Knowledge Fabric`
   - 本地文件、网页、连接器、资料集、检索与深度研究

3. `Desktop Operations Engine`
   - 对桌面软件、浏览器、CLI 和 API 的统一操作能力

4. `Memory Palace`
   - 历史任务、对话、决策原因、失败记录、用户偏好

5. `Council Orchestrator`
   - 多 Agent 的规划、审议、派发、监控和人工干预

6. `Scenario Sandbox`
   - Mission 级 baseline / option 对比、结构化 option card 存储、recommendation 兜底；变量注入和解释层仍在补齐

7. `Growth Engine`
   - 任务复盘、流程抽取、技能建议、个体学习画像

## 10. 创新组合方案

这款产品最重要的不是“集成了哪些项目”，而是以下六个组合创新：

### 创新 1：桌面软件操作是一等公民

来自 `hermes-agent + TuriX-CUA`

`Hermes Operator` 的首要能力不是聊天、不是知识库、也不是仪表盘，而是：

- 理解用户目标
- 接管桌面上下文
- 实际打开和操作软件
- 回收执行结果并继续下一步

这会把产品从“桌面上的 AI 助手”变成“真正替用户动手的软件操作员”。

### 创新 2：Hermes 功能等价基线 + TuriX 超越目标

来自 `hermes-agent + TuriX-CUA`

产品架构上，不复用任何现有代码。核心要求是：

- 用 Rust 绿地重写一个与 `hermes-agent` 功能和行为等价的 Agent Core
- 把 `TuriX-CUA` 作为桌面操作 benchmark
- 在桌面操作能力上系统性超越 TuriX

其他项目都不作为主干，而是按需叠加：

- `mempalace` 解决记忆深度
- `onyx` 解决知识广度
- `edict` 解决多 Agent 治理
- `MiroFish` 解决结构化变量推演、scenario comparison、saved-run comparison matrix、path evolution 和 recommendation 解释
- `DeepTutor` 解决成长闭环

这能避免产品变成多个 AI 项目的拼装盘，也避免产品沦为单纯的“包壳集成器”。

### 创新 3：可见可控的多 Agent 治理

来自 `edict + hermes-agent`

大多数多 Agent 产品的问题不是不能协作，而是用户看不懂它们在干什么。新产品引入审议机制与任务看板：

- 哪个 Agent 负责什么
- 当前任务在哪个阶段
- 为什么某个方案被退回
- 哪一步需要用户确认

这会显著提升信任感与可复盘性。

### 创新 4：CLI + GUI 的混合操作网

来自 `hermes-agent + TuriX-CUA`

纯 API 工作流覆盖不了真实桌面场景，纯 GUI 自动化又很脆弱。新产品采用执行优先级：

API -> CLI -> Browser Automation -> Desktop GUI

能调用稳定接口时不用视觉点击；必须跨桌面应用时再进入 GUI 模式。这样既保留 TuriX 的闭环执行能力，也控制执行成本与脆弱度。

### 创新 5：逐字级项目记忆

来自 `mempalace + hermes-agent`

绝大多数 Agent 的记忆只留下“偏好标签”和“摘要结论”，这不足以支撑复杂长期任务。新产品保留：

- 原始决策对话
- 审议意见
- 执行失败原因
- 关键产物与上下文关联

这让系统不仅记住“做了什么”，也记住“为什么这样做”。

### 创新 6：任务完成后的成长机制

来自 `DeepTutor + hermes-agent`

每次完成 Mission 后，系统自动进入轻量复盘：

- 此次任务属于哪类模式
- 哪些步骤可抽为流程模板
- 哪些决策可写入记忆
- 是否形成新技能、新提示词、新检查单

这样桌面 Agent 会从“任务执行器”进化为“个人工作方法放大器”。

## 11. 首版产品范围

### 11.1 MVP（首个对外版本）必须包含

1. 桌面 Mission 工作台
2. 桌面软件操作能力作为一等公民
3. 本地资料接入与统一检索
4. 长时记忆与历史回溯

### 11.2 V1.1 应加入

1. Mission 级 comparison matrix 和 path evolution（基于已保存的 scenario runs）
2. 变量注入和 cross-scenario comparison
3. recommendation explanation / rationale card
4. 定时任务与后台驻留
5. 跨渠道通知与回传

其中：

## 13. 商业化与价值兑现思路

虽然当前任务是产品设计，不是商业计划，但产品定义必须考虑价值兑现方式。

建议商业化分层：

- 免费版：单用户、本地优先、基础检索、基础执行、基础记忆
- Pro 版：高级推演、更多执行器、更多连接器、后台任务、技能市场
- Team 版：共享知识、共享模板、组织治理、审计与协同

## 14. 成功指标

首版应重点衡量以下指标：

- 用户每周完成的端到端 Mission 数
- 一个 Mission 从创建到交付的平均时长
- 执行前进入推演/审议流程的比例
- 自动执行步骤占比
- 记忆召回被用户采纳的比例
- 任务后被沉淀为模板或技能的比例
- 7 日与 30 日留存

## 15. 主要风险与规避策略

### 风险 1：产品范围过大

规避策略：

- 严格围绕 Mission 闭环设计
- 首版只做高价值知识工作流
- 不把产品做成“所有 AI 项目功能的博物馆”

### 风险 2：GUI 执行不稳定

规避策略：

- 优先使用 API / CLI
- GUI 仅作为最后兜底执行层
- 高风险动作必须审批

### 风险 3：推演能力容易失真

规避策略：

- 把推演结果作为决策参考，而不是事实预测
- 明确展示变量、假设和置信度
- 引入对比试验与反方观点

### 风险 4：记忆系统带来隐私顾虑

规避策略：

- 本地优先
- 明确可见的记忆管理页
- 支持项目级禁记忆、手动删除、敏感项屏蔽

## 16. 产品路线总结

`Hermes Operator` 不应该被设计成“会聊天的桌面版 Hermes”，而应该被设计成：

**一个以 Rust 绿地重写的 Hermes 等价 Agent Core 为基础、把桌面软件操作作为产品主线、并以超越 TuriX 为重点目标，同时按需叠加知识、记忆、治理、推演和成长能力的桌面执行系统。**

如果要用一句更具产品感的话概括：

**它不是帮用户问问题，而是帮用户把复杂工作做成。**
